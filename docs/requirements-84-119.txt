==================================================
84. 適応型アセスメントを中核機能として実装
==================================================

固定された質問票だけではなく、

「利用者の回答に応じて、次の質問をAIまたは適応アルゴリズムが選択・生成する」

Adaptive Assessment Engineを実装してください。

目的は医学的診断ではありません。

目的：

「この利用者に対して、業務マニュアルをどのように表示すれば
最も理解しやすく、間違いにくいか」

を推定することです。


診断対象ではなく、以下の能力・表示適性・情報処理傾向を推定します。

・日本語文章の理解しやすさ
・ひらがなの読みやすさ
・カタカナの読みやすさ
・漢字の読みやすさ
・語彙難易度
・短文 / 長文理解
・否定文の理解
・条件文の理解
・手順の順序理解
・数字の読み取り
・単位の理解
・時刻・時間表現
・図と文章の対応
・アイコン理解
・視覚情報の利用
・文章情報の利用
・一度に扱いやすい情報量
・手順分割の必要度
・重要情報の見落としやすさ
・注意事項の認識
・記憶負荷を下げる必要性
・ふりがなの必要度
・文字サイズ
・行間
・強調表示の効果
・1画面1タスクの有効性

これらから

ManualPresentationProfile

を生成してください。


==================================================
85. 最初のスクリーニング
==================================================

初回テストの最初は、非常に簡単な項目から始めてください。

いきなり難しい漢字や長文を表示しないこと。

例えば：

STEP 1
日本語を使う頻度・希望言語

STEP 2
ひらがなの簡単な文章

STEP 3
基本的な漢字を含む文章

STEP 4
簡単な指示理解

STEP 5
図と文章の比較

のように段階的に確認してください。


例：

「ボタンを おしてください」

Q:
何をしますか？

A. ボタンを押す
B. ボタンを引く
C. 何もしない


次：

「赤いボタンを押してください」

次：

「作業開始前に、主電源を確認してください」

というように、
回答状況によって難易度を上げてください。


==================================================
86. 漢字理解を推定
==================================================

単純に

「この漢字を読めますか？」

だけで判定しないでください。

以下を組み合わせてください。

A. 読みの選択

例：

「確認」

○ かくにん
○ かくじん
○ こうにん


B. 文脈理解

「作業前に安全を確認する」

この文で最初にすることは？

○ 安全を確認する
○ 作業を終了する
○ 電源を切る


C. 表記比較

どちらが読みやすいですか？

A:
使用前に装置を確認してください

B:
使う前に、きかいを確認してください


D. ふりがな効果

確認
確認（かくにん）

のどちらで理解速度・正答率が改善するか確認。


単純な正答数だけでなく、

・正答率
・回答時間
・ふりがなによる改善
・文脈あり / なしの差

をプロフィール生成に使用してください。


==================================================
87. 日本語理解レベル
==================================================

日本語理解を単一の

JapaneseLevel = 1〜5

だけで保存しないでください。

少なくとも以下に分解してください。

{
  "hiragana_reading": 0.0-1.0,
  "katakana_reading": 0.0-1.0,
  "kanji_reading": 0.0-1.0,
  "vocabulary_comprehension": 0.0-1.0,
  "sentence_comprehension": 0.0-1.0,
  "instruction_comprehension": 0.0-1.0,
  "negation_comprehension": 0.0-1.0,
  "conditional_comprehension": 0.0-1.0
}

ただし値は絶対的な能力診断ではなく、

Manu-Tailor内で表示方法を決めるための推定値

として扱ってください。


==================================================
88. 特に重要な否定表現テスト
==================================================

業務マニュアルでは否定文の理解が非常に重要です。

例：

「電源を切らないでください」

Q:
正しい行動は？

A. 電源を切る
B. 電源を切らない


別形式：

「ランプが点灯するまでボタンを押さないでください。」

いつボタンを押しますか？

など。


ただし誤答した場合でも
利用者に危険作業を行わせるものではなく、
あくまでテスト用の仮想問題としてください。


negation_support

というプロフィール値を持たせ、

理解しづらい場合はマニュアル生成時に

❌ 電源を切る

ではなく

✓ 電源はそのままにしてください

など、
誤解しにくい肯定形への言い換えを優先してください。

ただし意味変更は禁止。


==================================================
89. 手順理解テスト
==================================================

順序理解を確認してください。

例：

1. 箱を開ける
2. 商品を取り出す
3. 箱を片付ける

カードを並べ替えてもらう形式を実装してください。


また、

「Aをした後にBをする」

「Bをする前にAをする」

なども比較してください。


推定：

sequence_support
step_granularity
one_action_per_step

等へ反映してください。


==================================================
90. 情報量に関するテスト
==================================================

同じ内容を、

A:
1つの長い文章

B:
3つの短い手順

で提示してください。


例：

A:
「電源を入れ、ランプが緑色になったことを確認してから
スタートボタンを押してください。」

B:

1. 電源を入れます。

2. ランプが緑色になるまで待ちます。

3. スタートボタンを押します。


どちらが

・正確に理解できたか
・速く理解できたか
・本人が読みやすいと感じたか

を測定してください。


主観だけでなく、
正答率と回答時間も利用してください。


==================================================
91. 図優位 / 文章優位テスト
==================================================

同じ作業を

A:
文章のみ

B:
文章 + 図

C:
図中心

で提示してください。

その後、
同じ理解確認問題を出します。


visual_support_effect

text_support_effect

を算出してください。


単純に

「図が好きですか？」

と質問するだけではなく、

実際の正答率や回答速度との差を利用してください。


==================================================
92. 記憶負荷の確認
==================================================

短い業務指示を提示してください。

例：

「青い箱を取り、机の右側に置いてください。」

数秒後、

「箱はどこに置きますか？」

等を確認。


次に、

1.
青い箱を取る

2.
机の右側に置く

のように分割して比較してください。


これは医学的なワーキングメモリ診断ではありません。

目的は

「マニュアルを何ステップまで一度に表示するのが適切か」

を推定することです。


==================================================
93. 回答時間を利用
==================================================

各設問について

shown_at
answered_at
response_time_ms

を記録してください。


ただし、

回答が遅い = 能力が低い

と単純判定してはいけません。


同一利用者内で

・形式A
・形式B

を比較する材料として利用してください。


例えば：

長文:
正解
8.4秒

短文:
正解
3.2秒

なら、

短文形式がより効率的

という判断材料にします。


==================================================
94. 正答率と好みを分離
==================================================

非常に重要です。

ユーザーが

「図が好き」

と言ったとしても、

実際には文章形式の方が正答率が高い可能性があります。


以下を別々に保存してください。

Preference
Performance


例：

visual_preference = 0.9

visual_performance_gain = 0.2


最終的な表示設定では、

本人の好み
+
実際の理解結果

の両方を利用してください。


==================================================
95. AIによる質問生成
==================================================

固定質問だけではなく、
LLMに新しい質問を生成させる機構を実装してください。

QuestionGeneratorAgent

を作成します。


入力：

・現在の推定プロフィール
・過去の回答
・現在の不確実性
・まだ十分測れていない能力
・難易度
・使用言語


出力：

次に最も情報量の高い質問候補。


例：

{
  "skill": "kanji_reading",
  "difficulty": 0.42,
  "question_type": "multiple_choice",
  "prompt": "作業前に安全を確認してください。",
  "question": "最初に何をしますか？",
  "choices": [
    "安全を確認する",
    "作業を終了する",
    "電源を切る"
  ],
  "correct_answer": 0
}


ただしAIが生成した問題を
そのまま利用者へ出してはいけません。

必ず検証工程を通してください。


==================================================
96. Question Validator
==================================================

QuestionValidatorを実装してください。

AI生成問題について、

・正解が一意か
・日本語として自然か
・問題文だけで解答可能か
・選択肢に曖昧性がないか
・難易度が適切か
・差別的 / 不快な内容がないか
・医学的診断を要求していないか
・危険な実作業を要求していないか

を確認してください。


Validatorに不合格の場合は

生成し直す

または

既存Question Bankから選択してください。


==================================================
97. Anchor Question
==================================================

全問題をAI生成にしないでください。

比較可能性を保つため、

人間が確認済みの

Anchor Questions

を用意してください。


例：

・基本ひらがな
・基本漢字
・否定文
・手順順序
・図と文章
・数字
・単位
・注意事項

など。


AI生成問題とAnchor Questionを組み合わせます。


例：

60〜80%:
検証済みQuestion Bank

20〜40%:
適応生成問題


比率は実装時に適切に調整してください。


==================================================
98. Question Bank
==================================================

以下のようなschemaでQuestion Bankを作ってください。

{
  "id": "...",
  "version": 1,
  "language": "ja",
  "skill_tags": [
    "kanji_reading",
    "instruction_comprehension"
  ],
  "difficulty": 0.35,
  "discrimination": 0.8,
  "question_type": "multiple_choice",
  "prompt": "...",
  "choices": [],
  "correct_answer": "...",
  "explanation": "...",
  "estimated_time_sec": 10,
  "validated": true
}


問題はVersion管理してください。


==================================================
99. Adaptive Question Selection
==================================================

次の質問をランダム選択しないでください。

現在最も不確実なプロフィール項目を優先してください。


例：

kanji:
かなり明確

visual_preference:
明確

negation_comprehension:
不確実

sequence_comprehension:
不確実


なら、

否定表現または順序理解の問題を優先します。


Information Gain
Bayesian update
Item Response Theory

等を検討してください。


PoCであっても、

if wrong:
    ask easier_question()

だけの単純ロジックより
一段高度な実装を目指してください。


==================================================
100. IRT / Bayesian Profile Estimation
==================================================

可能であれば、

Item Response Theory

または

Bayesian estimation

を導入してください。


各能力について

estimated_value
confidence
sample_count

を保持します。


例：

{
  "kanji_reading": {
    "estimate": 0.68,
    "confidence": 0.84,
    "samples": 5
  }
}


単に

3問中2問正解だから66%

とはしないでください。


==================================================
101. Confidenceを重視
==================================================

プロフィール値だけでなく、
推定の確信度を保存してください。


例：

kanji_reading:
0.71

confidence:
0.92


一方、

diagram_comprehension:
0.60

confidence:
0.31


なら、

後者について追加質問を出します。


テスト終了条件にも
confidenceを利用してください。


==================================================
102. テスト終了条件
==================================================

固定で必ず20問出すのではなく、

必要な情報が十分集まったら終了してください。


通常モード目標：

約3分


より詳細に設定したい利用者には、

「もう少し詳しく調べる」

オプションを用意してください。


例：

Quick:
約3分

Detailed:
5〜10分


Quick終了時でも
不足情報はデフォルト値で安全側に設定してください。


==================================================
103. 苦手領域の推定
==================================================

テスト終了後、

「あなたは○○障害です」

等の表示は禁止します。


代わりに、

「この表示方法が合いそうです」

として表示してください。


例：

✓ 短い文章
✓ 1手順ずつ表示
✓ 漢字にはふりがな
✓ 図と文章を併用
✓ 重要な注意事項を大きく表示


管理者向け画面では、

・長文理解で時間がかかる傾向
・否定文では追加確認を推奨
・図付き説明で正答率が改善

等の形で確認可能にしてください。


==================================================
104. 利用者への結果表示
==================================================

利用者にはスコア表だけを見せないでください。


例：

━━━━━━━━━━━━━━━━

あなたに合いそうな表示

📖 文章
短め

🧩 手順
1つずつ

🔤 漢字
ふりがなあり

🖼 図
多め

⚠ 注意
大きく目立たせる

[この設定で使う]

[自分で調整する]

━━━━━━━━━━━━━━━━


技術的な内部スコアは
管理画面または開発者画面のみで確認可能にしてください。


==================================================
105. 誤答時のUX
==================================================

テストは学校の試験のように感じさせないでください。

「不正解です」

を大きく表示する必要はありません。


基本的には

回答
↓
次の問題

と進めてください。


利用者に

「能力を試されている」

という印象を与えすぎないUXにしてください。


タイトルも

「認知能力テスト」

ではなく、

「あなたに合う表示を見つけます」

等にしてください。


==================================================
106. 小規模モデルの導入検討
==================================================

LLMですべてを判断する必要はありません。

むしろプロフィール推定については、
小規模な専用モデルの方が適している可能性があります。


以下を比較してください。


OPTION A:
ルール + Bayesian / IRT

OPTION B:
Logistic Regression

OPTION C:
LightGBM / XGBoost

OPTION D:
小規模ニューラルネットワーク

OPTION E:
小型Language Model


最初の実装では

Bayesian / IRT
+
小規模分類・回帰モデル

を第一候補としてください。


利用データが十分集まっていない段階で
巨大なニューラルネットを学習しないでください。


==================================================
107. Profile Prediction Model
==================================================

将来的には回答履歴から、

・最適文字サイズ
・最適文章長
・ふりがなの必要性
・図の有効性
・1画面あたりの最適手順数
・警告強調の必要度

を予測する小規模モデルを実装可能にしてください。


入力例：

question_features
answer_correct
response_time
selected_preference
comparison_result


出力：

recommended_display_parameters


モデルは

models/profile/

以下へ保存してください。


==================================================
108. 小型LLMを使う場合
==================================================

小型LLMは

「ユーザーの能力判定」

そのものよりも、

・問題生成
・文章難易度調整
・選択肢生成
・問題の言い換え

に利用してください。


スコアリングはできる限り
決定論的 / 統計的に行ってください。


ローカルモデルを利用する場合は、

0.5B〜3B程度の小型Instruction Model

等を候補にできます。


ただし、
モデルをゼロから学習することは第一選択としません。

必要なら

既存小型モデル
+
LoRA / fine-tuning

を検討してください。


==================================================
109. AIによる問題難易度制御
==================================================

問題生成時に以下を指定できるようにしてください。

target_skill
target_difficulty
sentence_length
kanji_level
vocabulary_level
number_of_steps
negation
visual_dependency


例：

Generate a Japanese instruction comprehension question.

Target:
kanji difficulty = easy
sentence length = short
steps = 1
negation = false

のように構造化してください。


自由な自然言語プロンプトだけで
難易度を制御しないでください。


==================================================
110. 問題特徴量
==================================================

各問題には、
自動算出できる特徴を保存してください。


例：

character_count
sentence_count
kanji_ratio
unique_kanji_count
average_sentence_length
number_count
unit_count
negation_count
step_count
image_present
choice_count


これらを後のモデル学習にも使用してください。


==================================================
111. 漢字難易度
==================================================

可能であれば日本語漢字の難易度を
単純な文字数だけではなく分類してください。


例：

・小学校低学年相当
・小学校高学年相当
・常用漢字
・業務専門語

など。


ただし教育能力を正式評価する用途ではなく、

「どの表記ならマニュアルが読みやすいか」

を推定するために利用します。


==================================================
112. AIが質問を作った理由
==================================================

デバッグ / 管理者画面では、

なぜその質問を選んだか

を確認できるようにしてください。


例：

Question 7

Target:
negation_comprehension

Reason:
confidence = 0.42で、
他項目より推定の不確実性が高いため。


これによりAdaptive Assessmentが
ブラックボックスにならないようにしてください。


==================================================
113. 評価結果からマニュアル生成設定へ直接反映
==================================================

Assessment結果を
説明文章にしてからLLMへ渡すだけにしないでください。


明示的な設定値へ変換してください。


例：

{
  "max_sentence_chars": 28,
  "steps_per_screen": 1,
  "use_furigana": true,
  "prefer_images": true,
  "font_scale": 1.25,
  "line_spacing": 1.7,
  "highlight_warnings": true,
  "rewrite_negation_when_safe": true,
  "use_bullets": true
}


この設定を
Manual Generation Engineが直接利用してください。


==================================================
114. 継続学習
==================================================

初回テストだけでプロフィールを固定しないでください。


実際にマニュアルを使った後、

・戻るを頻繁に押す
・原文を頻繁に確認する
・特定ステップで滞在時間が長い
・文字サイズを変更する
・図を拡大する
・ふりがなをONにする

等があれば、

利用者本人の許可された範囲で
プロフィール改善の参考情報として利用可能な設計にしてください。


ただし自動的に大きく設定変更せず、

「こちらの表示の方が読みやすそうです。変更しますか？」

と提案する方式を優先してください。


==================================================
115. Privacy
==================================================

アセスメント結果はセンシティブな可能性があります。

必要以上に

・障害名
・病名
・能力ラベル

を保存しないでください。


保存するのは原則として

「マニュアル表示に必要な設定」

と

「その設定を推定するためのテスト結果」

です。


管理者が必要以上に個人の能力を順位付けできるUIを作らないでください。

119. 重要な設計原則
==================================================

AIに

「この人は漢字が苦手そう」

と自由推論させてプロフィールを決めさせないでください。


必ず

観測された回答
+
質問の特徴量
+
正誤
+
回答時間
+
比較テスト
+
統計モデル

から推定してください。


LLMの役割：

問題生成
言い換え
問題候補生成

統計モデルの役割：

能力 / 表示適性の推定


この役割分担を守ってください。
